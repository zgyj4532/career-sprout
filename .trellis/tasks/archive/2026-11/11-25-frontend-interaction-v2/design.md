# Frontend Refactor v2.0 — Approval Draft

## Workspace navigation
Retain the desktop rail with visible task labels and active state. Trim its current 240px footprint and decorative padding; switch to the mobile shell before the main form needs to compress, rather than forcing a tablet-width rail. Desktop rail is for frequent cross-task navigation, not for page-level tools. Top navigation could reclaim width but would compete with page controls and does not fix parallel content panes; it is not the proposed cutover. Keep Home, authentication and focused interview-session shells distinct.

On phones, preserve four labelled bottom destinations; a light top row provides Home, history and account, not a second main navigation. Keep content in normal vertical flow, account for the safe area, and avoid adding a second fixed action bar over the bottom navigation. When the keyboard consumes the viewport, suppress or reposition fixed chrome as needed while leaving form actions reachable by scroll. Two profile links must wrap or stack rather than require a swipe.

## Page behavior
- **了解自己:** two addressable, mutually exclusive screens with a visible two-link switch below the heading, not two columns or two steps. “个人档案” holds basic details, education, experiences, skills and the existing save action. “导入与授权” holds import/recovery, class advising and sharing controls, with their current status and consent wording. `/profile` stays the default/legacy destination; use a dedicated view query (e.g. `/profile?view=materials`) for the alternate screen, preserving other parameters. Browser Back/Forward switch screens; no prerequisite to switch either way.
- **找个方向:** a list with divider rows and a labelled add action; screenshot import is an explicit alternative to manual entry, not a competing large card. List and job detail/editor occupy the same region at different times. Restore page position and pagination on return. Preserve job requirements, gap results and related handoffs.
- **做简历:** borrow the Europass dashboard distinction between a document entry point and a broad working area, not its card grid or a presumed editor layout. Default to one editing area; keep “导入简历” and “已保存版本” as visible, separate entries, not a permanent sidebar. Keep save, continue and confirmed PDF alongside editing. A tool switch is not a record switch; choosing another record retains confirmation. Distinguish saved and targeted versions. Show AI review only after a suggestion, with local side-by-side comparison when it fits and stacked original/suggestion on narrow screens.
- **练面试:** collapse preparation cards into sections for materials and practice settings with one primary start action. During practice, prioritize the current question and answer; keep recording/transcription status visible when active, and feedback at the appropriate point. Preserve confirm-before-advance and the exit guard.

## Visual hierarchy
Keep existing campus colors and typography. Use a heading and one visually primary action per task state, with space and dividers grouping ordinary sections. Use list rows for repeated records; keep a distinct surface for genuinely interactive review, warning or empty state. Do not wrap every explanatory sentence or form group in a card, nest decorative cards or restyle dormant workflows.

## Boundaries and accessibility
Keep the router, basename, lazy boundary, providers and API. Profile view navigation must keep a single page owner for unsaved edits and requests; do not reset the owner by query key. The existing `UnsavedWorkProvider` blocks any changed location when dirty (`frontend/src/campus/components/UnsavedWorkProvider.jsx:11-18`). Allow only the dedicated same-profile view transition, including Back/Forward, while retaining guards for actual leave, other query changes and reload. Do not silently bypass dirty import protection. Keep validation and recovery visible on the relevant screen; preserve an active import or recording when changing view and never imply that a hidden operation is saved. Preserve resume query-driven import/recovery. Maintain accessible names, visible focus and predictable focus after view navigation; use normal vertical reflow instead of nested scrolling.

## Trade-offs and rollback
The rail uses desktop width in exchange for labelled one-click navigation; phones use bottom navigation without squeezing the main task. Secondary document tools can take one extra click; retain dedicated links rather than hiding everything under “More”. Revert by shell/page commit if needed; no data migration or feature flag.
