# Docker build diagnostics (2026-11-06)

## Environment evidence

- Docker CLI/engine 29.7.2; default Buildx builder uses driver `docker`, BuildKit v0.32.2, linux/amd64.
- Docker engine proxy is configured at loopback `127.0.0.1:7897` for HTTP and HTTPS. TCP on that port is open from WSL host and from a container using host networking. A test tarball request through it returned HTTP 200 in 1079 ms. Never print/store credentials if the proxy endpoint changes to include them.
- Engine reports registry mirrors `https://docker.m.daocloud.io/` and `https://docker.1ms.run/`; both Node and Nginx base images are already cached locally.
- Direct WSL checks: `npm ping` returned PONG in 1556 ms; npm and Debian index host requests returned HTTP 200. Registry API v2 returned HTTP 401, expected without credentials.
- Frontend `.npmrc` is `legacy-peer-deps=true`; retain it and `npm ci`.

## Observed outcomes

- Exact frontend Dockerfile build, 300-second bound, `--progress=plain --network=host`, unique tag and non-deployable fake `pk_live_`: entered `RUN npm ci`, emitted two deprecation warnings, then no further visible progress before timeout. No image.
- Temporary verbose install-only build used the exact lockfile and `.npmrc`, Node 24.22.2/npm 11.19.1, `npm ci --loglevel verbose --fetch-retries=0 --fetch-timeout=20000`, 240-second overall cap. Logs showed many cache hits and live `GET 200` requests from `registry.npmjs.org`; successful fetch timings were about 46–54 seconds. Build timed out before completion; verbose output was truncated. No image.
- Same 24.8 kB React tarball download over direct npm registry took 1634 ms. `registry.npmmirror.com` redirects to `cdn.npmmirror.com`; same tarball from that CDN took 80 ms in WSL and 94 ms from a host-network container. This one-artifact spot check only proves that CDN route is faster for this sample, not full lockfile reliability.
- Bounded diagnostic `npm ci --registry=https://registry.npmmirror.com/` completed in 23 seconds and installed 828 packages, but then Puppeteer's postinstall failed trying to download Chrome: the Linux Node image lacked an archive extraction binary. This was a diagnostic-only Dockerfile without the production Dockerfile's `PUPPETEER_SKIP_DOWNLOAD=true`. A second bounded attempt with that setting completed `npm ci` successfully in 23 seconds. This proves the mirror-assisted install path works with the backend-aligned Puppeteer browser policy; it does not by itself prove the full frontend build succeeds.
- Apt diagnostic with retries disabled: `apt-get update` fetched 9.4 MB in 57 seconds (~165 kB/s). A separate FFmpeg-only install resolved 200 packages / 134 MB and downloaded 32 packages (~5.8 MB) in the remaining 100-second window before timeout. Original Chromium/FFmpeg/fonts install is larger (~329 MB reported earlier). This is slow upstream transfer, not an apt deadlock.
- Full frontend image, tag `career-sprout-frontend:diagnostic-nondeployable-20261106b`, built successfully; build-time npm installed 828 packages in 78 seconds, Vite transformed 551 modules and built successfully. BuildKit did not apply the attempted `NPM_CONFIG_REGISTRY` override because the Dockerfile does not declare that ARG; the successful full build therefore exercised the default registry with a dummy public key. Image size 85,011,268 bytes, image config labels it with the fake diagnostic key. It is explicitly non-deployable and must not be transferred.
- An isolated one-off Nginx container with a unique loopback binding on `127.0.0.1:18085`, matching dummy `CLERK_PUBLISHABLE_KEY`, served `/career-sprout/`, `/career-sprout/auth`, and the built hashed JS asset with HTTP 200. The initial smoke used the old image (Nginx listened on 80 while the container target was 8080) and got 502; a host-network attempt collided with host port 8080 and got 404. The image's `frontend/nginx.conf` fix now listens on 8080 and supplies the base-path SPA fallback. The successful final smoke used port mapping and HTTP no-proxy on loopback; exact smoke container removed.
- Dedicated Redis image built successfully as `career-sprout-redis:local-diag-20261106`, size 16,253,462 bytes.
- First full backend build used direct apt and timed out after 900 seconds, without an image. It fetched 9.4 MB of indexes in 51 seconds, resolved 266 packages / 329 MB, and reached Chromium package downloads before BuildKit cancelled. A retry supplied upper/lowercase HTTP(S) proxy build args, but apt still fetched from `deb.debian.org`: 9.4 MB of indexes took 6m05s (25.7 kB/s), and package downloads remained slow. After 1500 seconds it had downloaded through package 149 of 266 (including retries) and BuildKit canceled at `libz3-4`; no backend image was produced. - Frontend and Redis images are local diagnostic artifacts; the frontend tag has a dummy key and is non-deployable. No server mutation, upload/deployment, commit, or push.

## Diagnosis and remedy

- Backend failure was network-bound, not an apt deadlock: `apt-get update/install` fetched ~329 MB from `deb.debian.org` at 25.7 kB/s in the proxy retry. A representative 9.38 MB package fetched from SJTU in 385 ms (~24.4 MB/s), and the full 266-package apt transaction completed in ~83 seconds from that mirror. HTTPS failed only because the base image has no trusted CA store; signed APT metadata over HTTP succeeded with verification enabled. After fixing apt throughput, `npm ci` exposed the separate missing `.npmrc` issue and failed with `ERESOLVE`; copying the repository's `legacy-peer-deps=true` config resolved it. Earlier frontend npm registry slowness is separate and the full frontend build succeeded using the default registry.

- Minimal remediation applied: `backend/Dockerfile.campus` rewrites only Debian's main/security Bookworm source URLs to the measured SJTU mirrors over HTTP (APT's signed metadata verification stays enabled), and copies `backend/.npmrc` before `npm ci`; no dependency or lockfile changes. The existing frontend fixes remain: skip Puppeteer's redundant browser download because backend supplies system Chromium, and serve `/career-sprout/` with the base-path SPA Nginx config. The successful full frontend image used the default npm registry; no permanent npm mirror change.
- Docker HTTP proxy reachability alone had been misleading: the configured proxy did not provide adequate sustained apt throughput for this route. Direct mirror measurements and a full signed apt transaction provided evidence for the source change. For npm, a representative Debian index probe was 0.44s direct vs. 1.34s through proxy; no npm mirror policy was changed.
- No justification for longer timeouts alone; they would mask low throughput.

## Official documentation consulted

- Docker client proxy configuration: https://docs.docker.com/engine/cli/proxy/ (proxy build args are pre-populated; avoid Dockerfile `ENV` because that persists configuration).
- Docker Buildx options: https://docs.docker.com/reference/cli/docker/buildx/debug/build/ (`--network`, `--progress=plain`; debug build command is experimental).
- npm v10 config docs (host npm 10.8.2): https://docs.npmjs.com/cli/v10/using-npm/config/ (`.npmrc`, config precedence, verbosity/fetch options).
- Debian Bookworm apt HTTP transport: https://manpages.debian.org/bookworm/apt/apt-transport-http.1.en.html (proxy configuration and `Acquire::http::Timeout`).
- Puppeteer configuration: https://pptr.dev/guides/configuration and https://pptr.dev/api/puppeteer.configuration (`PUPPETEER_SKIP_DOWNLOAD`/skipDownload controls).
